# Шпаргалка: `systemctl`

**`systemctl`** — главная утилита для управления системой инициализации **systemd**. Она отвечает за контроль сервисов (служб), проверку их статуса, автозагрузку и управление состоянием сервера (перезагрузка/выключение).
## 🚀 Управление сервисами (Основные команды)

Вместо `unit.service` можно писать просто имя сервиса (например, `nginx` или `docker`).

- `systemctl start unit` — **запустить** сервис.
- `systemctl stop unit` — **остановить** сервис.
- `systemctl restart unit` — **перезапустить** сервис (полная остановка и запуск).
- `systemctl reload unit` — **перезагрузить конфигурацию** без остановки самого сервиса (если поддерживается приложением).
- `systemctl status unit` — **проверить статус** (активен, выключен, логи, PID и потребление памяти).
## 🔄 Управление автозагрузкой

- `systemctl enable unit` — добавить сервис в **автозагрузку** при старте ОС.
- `systemctl disable unit` — убрать сервис из автозагрузки.
- `systemctl is-enabled unit` — проверить, находится ли сервис в автозагрузке.
## 🔍 Мониторинг и поиск юнитов

- `systemctl list-units --type=service` — показать все **активные** сервисы в системе.
- `systemctl list-unit-files --type=service` — показать вообще все доступные сервисы и состояние их автозагрузки (`enabled`/`disabled`).
- `systemctl --failed` — показать все юниты, которые **завершились с ошибкой**.
## ⚠️ Важные команды администратора

- `systemctl daemon-reload` — **обязательная команда** после изменения `.service` файлов конфигурации. Перечитывает конфигурацию systemd с диска.
- `systemctl mask unit` — полностью заблокировать сервис (его нельзя будет запустить даже вручную или через другие зависимости).
- `systemctl unmask unit` — снять блокировку сервиса.
## 💻 Управление питанием сервера

- `systemctl reboot` — перезагрузить сервер.
- `systemctl poweroff` — выключить сервер.

# А как вообще systemctl имеет доступ к каким то разрабатываемым сервисам? Может ли он запускать контейнер Docker? Как он их видит?

`systemctl` ничего не ищет "вслепую" и сам по себе про твои кастомные сервисы или контейнеры Docker ничего не знает. Чтобы он их «увидел», их действительно **нужно зарегистрировать** — но делается это очень просто, через текстовые файлы конфигурации.

Вот как устроена эта магия изнутри:
## 1. Как systemd видит сервисы? (Юниты)

Вся работа `systemd` построена на **юнитах (units)**. Юнит — это обычный текстовый файл с расширением `.service`, в котором написано: _что запускать, от какого пользователя, и когда._

`systemd` сканирует строго определенные папки на диске. Чтобы утилита `systemctl` увидела твой разрабатываемый сервис, тебе достаточно положить туда файл конфигурации.

- **Главная папка для твоих сервисов:** `/etc/systemd/system/`
- Например, ты создал файл `/etc/systemd/system/my-app.service`.
- После этого ты выполняешь команду `systemctl daemon-reload` (она заставляет systemd перечитать папки), и всё — `systemctl start my-app` начинает работать.

## 2. Как выглядит этот файл? (Пример для Go/Python/Node.js приложения)

Допустим, ты написал свой бэкенд-сервис и скомпилировал бинарник. Твой `.service` файл в `/etc/systemd/system/` будет выглядеть примерно так:

Ini, TOML

``` TOML
[Unit]
Description=My Golang Backend Service
After=network.target # Запускать только после того, как поднимется сеть

[Service]
Type=simple
User=www-data
WorkingDirectory=/var/www/my-app
ExecStart=/var/www/my-app/backend-binary --config=prod.json
Restart=always # Если бэк упадет (panic), systemd сам его поднимет!
RestartSec=5

[Install]
WantedBy=multi-user.target # Нужно для автозагрузки
```

## 3. Может ли `systemctl` запускать контейнеры Docker?

**Да, абсолютно.** И в продакшене это часто практикуется.

Сам Docker работает в Linux как... правильно, такой же сервис systemd (`docker.service`). Но ты можешь завернуть управление конкретным контейнером в юнит `systemd`.

В таком случае в секцию `ExecStart` прописывается стандартная команда запуска контейнера:

Ini, TOML

``` TOML
[Service]
# Перед запуском на всякий случай удаляем старый контейнер
ExecStartPre=-/usr/bin/docker rm -f my-postgres-container
# Запускаем контейнер (без флага -d, чтобы systemd контролировал процесс)
ExecStart=/usr/bin/docker run --name my-postgres-container -p 5432:5432 postgres:15
ExecStop=/usr/bin/docker stop my-postgres-container
```

**Зачем это надо?** Например, чтобы твой контейнер автоматически стартовал при включении сервера, или чтобы настроить строгую последовательность: _«сначала systemd запускает локальную БД в Докере, и только после её успешного старта запускает твой бинарник бэкенда»_.

## 🗂️ Итоговая схема: как это работает в ОС

1. **Разработчик** пишет код ➔ компилирует бинарник (или упаковывает в Docker).
2. **Разработчик/Админ** создает `.service` файл в `/etc/systemd/system/`.
3. Выполняется `systemctl daemon-reload`.
4. Теперь `systemctl` знает о сервисе. Когда ты пишешь `systemctl start my-app`, `systemd` считывает файл, находит строчку `ExecStart`, делает системный вызов `fork` ядра Linux, понижает права до указанного `User` и запускает твой процесс, забирая его логи в `journalctl`.
