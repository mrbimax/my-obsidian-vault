# Шпаргалка: `journalctl`

**`journalctl`** — утилита для просмотра и анализа логов, которые собирает системная служба **systemd-journald**. В отличие от старого текстового `/var/log/syslog`, `journalctl` работает с бинарными логами, что делает поиск, фильтрацию и индексацию моментальными.

## 🔍 Базовый просмотр

- `journalctl` — показать вообще все логи системы (начиная с самых старых).
- `journalctl -n 50` — показать только последние **50 строк** логов.
- `journalctl -f` — режим **слежения в реальном времени** (аналог `tail -f`).

## ⚙️ Фильтрация по сервисам и процессам

Самый частый кейс на бэкенде — дебаг конкретного приложения.

- `journalctl -u my-app.service` — логи конкретного **сервиса**.
- `journalctl -u my-app.service -f` — смотреть логи сервиса **в реальном времени**.
- `journalctl _PID=1234` — фильтрация логов по конкретному **ID процесса**.

## 📅 Фильтрация по времени (Таймфреймы)

Флаги `--since` (с тех пор как) и `--until` (до тех пор как) понимают как точные даты, так и человекочитаемые строки.

- `journalctl --since "yesterday"` — логи с начала вчерашнего дня.
- `journalctl --since "1 hour ago"` — логи за последний час.
- `journalctl --since "2026-06-01 12:00:00" --until "2026-06-01 13:00:00"` — логи за конкретный промежуток времени.

## 🚨 Фильтрация по уровню ошибок (Severity)

Флаг `-p` (priority) позволяет отсечь лишний флуд (информационные логи) и смотреть только проблемы. Используются стандартные уровни (0-7) или их имена: `emerg` (0), `alert` (1), `crit` (2), `err` (3), `warning` (4), `notice` (5), `info` (6), `debug` (7).

- `journalctl -p err -b` — показать только **ошибки** (Error) с момента последней загрузки системы.
- `journalctl -u nginx.service -p warning` — показать только предупреждения и ошибки для Nginx.

## 💾 Дополнительные фичи

- `journalctl -b` — показать логи только с момента **последней загрузки** сервера (очень удобно, чтобы не листать историю за прошлый месяц).
- `journalctl -b -1` — логи за предыдущую сессию (до прошлой перезагрузки).
- `journalctl -k` — показать только логи **ядра Linux** (dmesg).
- `journalctl --disk-usage` — узнать, сколько места на диске занимают логи прямо сейчас.

# Откуда у утилиты доступ к логам?

Утилита `journalctl` сама по себе не занимается сбором логов — она является лишь «клиентом» (интерфейсом) для чтения данных. Вся магия происходит на уровне ядра Linux и системного демона **`systemd-journald`**.

Вот как устроена эта цепочка изнутри:

## 🏗️ Архитектура сбора логов

Когда твое приложение (например, на Go) пишет лог через стандартный вывод (`fmt.Println` или любой логгер в `stdout`/`stderr`), происходит следующее:

```
[ Твое приложение ] 
       │
       │ (пишет в stdout / stderr)
       ▼
[ Ядро Linux ] ➔ перехватывает потоки благодаря systemd
       │
       ▼
[ systemd-journald ] (демон-сборщик логов)
       │
       ├─► Обогащает лог метаданными (PID, UID, Время, Имя сервиса)
       ├─► Сжимает и записывает в бинарный формат (.journal)
       ▼
[ Диск: /var/log/journal/ ] 
       ▲
       │ (читает файлы конфигурации)
[ journalctl ] ➔ парсит бинарники и красиво выводит тебе в консоль
```

## 🛠️ За счет чего это работает?

### 1. Перехват stdout/stderr

Когда `systemd` запускает твой сервис (на основе того самого `.service` файла, о котором мы говорили ранее), он подменяет стандартные дескрипторы вывода процесса (`stdout` и `stderr`). Вместо того чтобы писать "в никуда", процесс пишет в специальные unix-сокеты или пайпы, которые слушает демон `systemd-journald`.

### 2. Обогащение данных (Метаданные)

Когда лог попадает в `systemd-journald`, демон не просто сохраняет строчку текста. Он обращается к ядру Linux и собирает контекст вокруг процесса.

Именно поэтому ты можешь фильтровать логи по флагам — в каждый лог намертво зашиваются:

- `_PID` — идентификатор процесса.
- `_UID` / `_GID` — от какого пользователя/группы запущен код.
- `_SYSTEMD_UNIT` — имя сервиса (например, `my-app.service`).
- Точное время с точностью до микросекунд.

### 3. Бинарное хранилище на диске

В отличие от старого демона `syslog`, который писал логи в обычные текстовые файлы (вроде `/var/log/syslog`), `journald` пишет логи в структурированном **бинарном формате** с индексацией. Они лежат в папке:

- `/run/log/journal/` (только в оперативной памяти — исчезают после перезагрузки).
- `/var/log/journal/` (персистентные логи на диске).
