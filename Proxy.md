## 1. [[Forward Proxy]] vs. [[Reverse Proxy]]

Главное отличие — **кого именно** защищает и маскирует прокси-сервер.

- **[[Forward Proxy]] (Прямой прокси)**
    - **Где стоит:** На стороне **клиента**.
    
    - **Зачем нужен:** Маскирует клиента от внешнего интернета. Помогает обходить блокировки, кешировать ответы для локальной сети или контролировать трафик сотрудников в офисе.
    
    - **Пример:** VPN, корпоративный прокси.
    
- **[[Reverse Proxy]] (Обратный прокси)**
    - **Где стоит:** На стороне **сервера** (бэкенда).
    
    - **Зачем нужен:** Маскирует ваши бэкенд-серверы от клиентов. Принимает запросы из интернета и решает, какому инстансу приложения их передать.
    
    - **Пример:** [[Nginx]], [[HAProxy]], [[Traefik]], [[Envoy]].

## 2. Зачем вам Reverse Proxy на бэкенде?

В продакшене запускать приложение (Node.js, Go, Python, Java) напрямую «наружу» — плохая практика. Вот что берет на себя обратный прокси:

- **Балансировка нагрузки (Load Balancing):** Распределяет запросы между несколькими инстансами вашего приложения (алгоритмы Round Robin, Least Connections и др.).
    
- **SSL/TLS Терминация:** Прокси берет на себя расшифровку HTTPS-трафика. До самого бэкенда запрос идет по обычному HTTP внутри закрытой сети. Это экономит ресурсы CPU бэкенд-серверов.
    
- **Раздача статики:** Прокси (особенно Nginx) отдает картинки, CSS и JS в разы быстрее, чем код вашего приложения. Бэкенд занимается только бизнес-логикой.
    
- **Безопасность:** Скрывает реальные IP-адреса ваших серверов, защищая их от прямых DDoS-атак. Здесь же можно настроить Rate Limiting (ограничение частоты запросов).
    

## 3. Критически важные HTTP-заголовки

Когда запрос проходит через прокси, для вашего бэкенда «клиентом» становится сам прокси (его IP-адрес). Чтобы не потерять данные о реальном пользователе, прокси должен прокидывать специальные заголовки:

|**Заголовок**|**Что содержит**|**Зачем нужен бэкенду**|
|---|---|---|
|`X-Forwarded-For`|Цепочка IP-адресов (`client, proxy1, proxy2`)|Чтобы знать **реальный IP пользователя** (для геолокации, банов, логирования).|
|`X-Real-IP`|Обычно IP-адрес самого первого клиента|Альтернатива/дополнение к `X-Forwarded-For` (содержит только один IP).|
|`X-Forwarded-Proto`|Протокол исходного запроса (`http` или `https`)|Чтобы бэкенд понимал, защищено ли соединение (например, для генерации правильных абсолютных ссылок).|
|`Host`|Оригинальный хост, запрошенный клиентом (например, `api.example.com`)|Чтобы бэкенд корректно обрабатывал маршрутизацию, если на одном коде крутится несколько сайтов (Multi-tenancy).|

> ⚠️ **Внимание на безопасность:** Никогда слепо не доверяйте заголовку `X-Forwarded-For`, если прокси не настроен на перезапись этого заголовка. Злоумышленник может подделать его в исходном запросе (IP Spoofing). Настраивайте прокси так, чтобы он сбрасывал или жестко контролировал этот заголовок.

## 4. Краткий гид по инструментам

- **Nginx:** Бессмертная классика. Идеален как веб-сервер, обратный прокси и для раздачи статики.
    
- **HAProxy:** Максимально производительный балансировщик нагрузки (работает на уровнях L4 и L7). Если нужно только распределять огромный трафик — это лучший выбор.
    
- **Traefik / Envoy:** Современные Cloud-Native прокси. Отлично подходят для микросервисов, Docker и Kubernetes, так как умеют автоматически подхватывать новые контейнеры и обновлять конфигурацию на лету.
    

## 5. Базовый конфиг Nginx (Шпаргалка для старта)

Классический пример настройки Nginx как Reverse Proxy для бэкенда, работающего на порту `8080`:

Nginx

``` nginx
server {
    listen 80;
    server_name api.yourdomain.com;

    # Ограничение размера загружаемых файлов
    client_max_body_size 20M;

    location / {
        # Куда перенаправлять трафик (наш бэкенд)
        proxy_pass http://127.0.0.1:8080;

        # Передача правильных заголовков бэкенду
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Настройки таймаутов (чтобы прокси не отваливался на долгих запросах)
        proxy_read_timeout 90s;
        proxy_connect_timeout 90s;
        proxy_send_timeout 90s;
    }
}
```
