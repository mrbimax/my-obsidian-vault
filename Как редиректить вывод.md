# Шпаргалка: Редирект вывода (Перенаправление потоков)

В Linux всё взаимодействие с процессами идет через три стандартных потока данных. Каждому потоку присвоен свой файловый дескриптор (File Descriptor — FD):

- **`0` (stdin)** — Стандартный ввод (клавиатура, потоки).
- **`1` (stdout)** — Стандартный вывод (то, что программа пишет при успешной работе).
- **`2` (stderr)** — Стандартный вывод ошибок (куда летят логи ошибок и паники).

## 🚀 Основные операторы перенаправления

### 1. Перенаправление успешного вывода (`stdout`)

- `command > file.txt` — **Перезаписать** файл. Если файл существовал, его содержимое сотрется. Если нет — он создастся.
- `command >> file.txt` — **Дописать в конец** файла. Старые данные не удаляются.
- `command 1>> file.txt` — То же самое что и выше


### 2. Перенаправление ошибок (`stderr`)

Чтобы отделить логи ошибок от обычных данных, используется дескриптор `2`.

- `command 2> errors.log` — Перезаписать ошибки в файл.
- `command 2>> errors.log` — Дописать ошибки в конец файла.

### 3. Объединение потоков (Всё в один файл)

Частый кейс для бэкенда: писать и логи, и ошибки в один `app.log`.

- `command > app.log 2>&1` — Классический способ. Перенаправляет `stdout` в файл, а затем поток `2` (`stderr`) отправляет туда же, куда идет поток `1`.
- `command &> app.log` — Современный сокращенный аналог предыдущей команды.
- `command &>> app.log` — Добавление и `stdout`, и `stderr` в конец одного файла.

## 🕳️ Черная дыра (`/dev/null`)

Если вывод команды или её ошибки тебе вообще не нужны в консоли, их можно отправить в специальное псевдоустройство-пустышку.

- `command 2> /dev/null` — Скрыть только ошибки (полезно при поиске через `find` или `grep`, чтобы не лезли строки "Permission denied").
- `command > /dev/null 2>&1` — Полностью "заглушить" команду (скрыть и вывод, и ошибки).

## 🚰 Пайплайн / Конвейер (`|`)

Оператор `|` (pipe) передает **stdout** первой команды на **stdin** второй команды.

Bash

``` bash
# Посмотреть процессы и отфильтровать нужный
ps aux | grep "go"

# Посмотреть логи в реальном времени и отсечь лишнее
journalctl -u app.service -f | grep --line-buffered "ERROR"
```

## 🔠 Перенаправление ввода (`stdin`)

Используется реже, когда нужно скормить файл команде, которая ожидает ввод с клавиатуры.

- `command < file.txt` — Передать содержимое файла на вход команде.
- `cat << EOF > config.yaml` — **Here-Doc:** запись многострочного текста в файл прямо из консоли до тех пор, пока не будет введено кодовое слово `EOF`.

## 🟢 Поток `1>` (Standard Output)

Когда ты пишешь просто знак **`>`**, система по умолчанию подставляет туда единицу. То есть:

- `command > file.txt` — это абсолютно то же самое, что и:
- `command 1> file.txt`

Писать `1>` вручную не нужно — оболочка автоматизирует этот процесс, экономя твоё время. Единицу указывают явно только тогда, когда нужно перенаправить оба потока в разные места одной командой:

Bash

``` bash
# Явное разделение: stdout в один файл, stderr в другой
command 1> success.log 2> errors.log
```

## 🔵 Поток `0<` (Standard Input)

С вводом (`stdin`) ситуация аналогичная. Знак **`<`** по умолчанию работает с дескриптором `0`.

- `command < file.txt` — это полная копия команды:
- `command 0< file.txt`

Цифра `0` опускается для лаконичности. Команда просто открывает файл на чтение и скармливает его в `stdin` процесса.

## 🔴 Почему же для ошибок всегда пишут `2>`?

А вот для потока ошибок (`stderr`) дефолтного знака «без цифры» не существует.

Если бы ты написал `command > errors.log`, система подумала бы, что ты хочешь записать туда успешный вывод (`stdout`). Поэтому, чтобы сказать ядру Linux: _"Эй, не трогай успешный вывод, заверни мне именно ошибки"_, администратор **обязан** явно указать дескриптор: **`2>`**.

### 📝 Шпаргалка-итог для Obsidian:

Bash

```
# Равнозначные сокращения в Linux:
command > file.txt   ➔   command 1> file.txt   # stdout
command < file.txt   ➔   command 0< file.txt   # stdin

# Не имеет сокращений (цифра 2 обязательна):
command 2> file.txt                            # stderr
```
