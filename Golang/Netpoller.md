**Netpoller (сетевой поллер)** — это подсистема рантайма Go, которая связывает синхронный код горутин с асинхронными механизмами мультиплексирования ввода-вывода операционной системы ([[epoll]] в Linux, [[kqueue]] в macOS, [[IOCP]] в Windows). Именно благодаря ему в Go концепция _«один сокет — одна горутина»_ работает с экстремальной производительностью без оверхеда на потоки ОС.

## 🚀 Архитектурный паттерн: Как это работает под капотом

Когда горутина (G) совершает сетевой ввод-вывод (например, `conn.Read()`), рантайм Go делает следующий трюк:

1. **Попытка неблокирующего чтения:** Пакет `internal/poll` делает системный вызов `read()` на дескрипторе сокета, который изначально переведен в неблокирующий режим (`O_NONBLOCK`).
2. **Парковка горутины (EAGAIN):** Если данных в сокете нет, ОС возвращает ошибку `EAGAIN` (или `EWOULDBLOCK`). Рантайм Go перехватывает её, привязывает текущую горутину к структуре `pollDesc` этого сокета и переводит G в состояние `_Gwaiting` (блокировка на сетевом поллере) с помощью вызова `gopark()`.
3. **Освобождение потока (M):** Физический поток ОС (M), на котором выполнялась эта горутина, освобождается и планировщик (GMP) отдает его под выполнение других готовых горутин. **Поток ОС не блокируется!**
4. **Регистрация в ОС:** Файловый дескриптор сокета регистрируется в сетевом поллере ОС (например, через `epoll_ctl`).

## 🔄 Как горутины «просыпаются»?

За опрос сетевого поллера отвечает функция `runtime.netpoll(delay int32) gList`. Она возвращает список горутин, чьи сокеты получили события безопасности или данных. Вызов `netpoll` встроен в несколько критических точек планировщика Go:

- **`findrunnable()` (Основной драйвер):** Когда логический процессор (P) не может найти работу в своей локальной очереди, в глобальной очереди или украсть у соседей (work stealing), он делает **блокирующий** вызов `netpoll()`. Поток засыпает в ожидании сетевых событий. Как только они появляются, готовые горутины забираются в работу.
    
- **`sysmon` (Системный монитор):** Фоновый поток ОС, который не зависит от планировщика GMP. Раз в 10 мс он делает **неблокирующий** вызов `netpoll()`. Если находятся готовые горутины, он сбрасывает их в глобальную очередь (`global runq`), чтобы их подхватили свободные потоки.
    
- **`schedule()`:** Периодически (раз в 61 такт планировщика) совершается неблокирующий вызов сетевого поллера, чтобы предотвратить голодание (starvation) сетевых горутин при высокой вычислительной нагрузке кластера.
    

## 🛠️ Специфика реализации на уровне ОС

Go абстрагирует системные вызовы через интерфейс в `runtime/netpoll.go`. Реализация зависит от платформы:

|**ОС**|**Механизм**|**Файл в исходниках Go**|**Особенности**|
|---|---|---|---|
|**Linux**|`epoll`|`runtime/netpoll_epoll.go`|Использует **Edge-Triggered (EPOLLET)** режим. Событие генерируется только при смене состояния сокета, поэтому рантайм обязан вычитывать данные до упора (`EAGAIN`).|
|**macOS/BSD**|`kqueue`|`runtime/netpoll_kqueue.go`|Использует фильтры `EVFILT_READ` и `EVFILT_WRITE`.|
|**Windows**|`IOCP`|`runtime/netpoll_windows.go`|Работает на портах завершения ввода-вывода (I/O Completion Ports). Начиная с Go 1.14+ сильно оптимизирован.|

## 🗂️ Ключевые структуры данных (Runtime)

Если заглянуть в исходный код `runtime/netpoll.go`:

### 1. `pollDesc` (Дескриптор опроса)

Это мост между системным файловым дескриптором (`fd`) и горутиной.

Go

```
type pollDesc struct {
    link *pollDesc // Связанный список для аллокатора
    fd   uintptr   // Системный файловый дескриптор сокета

    // Семафоры для парковки горутин
    rg uintptr // Статус/Указатель на горутину, ожидающую чтение (Read Go)
    wg uintptr // Статус/Указатель на горутину, ожидающую запись (Write Go)

    rtimer timer // Тайм-аут на чтение
    wtimer timer // Тайм-аут на запись
}
```

_Вместо прямых указателей на G в полях `rg` и `wg` используются атомарные состояния (`pdReady`, `pdWait`) или упакованные адреса горутин для предотвращения Race Condition._

### 2. `pollCache`

Рантайм не выделяет `pollDesc` через обычный Garbage Collector (GC) при каждом новом соединении. Используется собственный пул объектов (`pollCache`) со связанными списками для минимизации аллокаций в куче (Heap Allocation) на уровне Highload-сетевого трафика.

## ⚙️ Поведение Netpoller при таймаутах (`SetDeadline`)

Когда вы вызываете `conn.SetReadDeadline(time.Now().Add(1 * time.Second))`:

1. Под капотом рантайм Go инициализирует таймер (`runtime.timer`), привязанный к `pollDesc`.
    
2. Если за 1 секунду данные в сокет не пришли, срабатывает хук таймера (`netpollReadDeadlineGlyph`), который принудительно переводит состояние `rg` в `pdReady`.
    
3. Горутина просыпается, пытается сделать системный вызов `read()`, но рантайм видит флаг истечения времени и возвращает ошибку `os.ErrDeadlineExceeded`.
    

## 💡 Важные инсайты для Highload-разработчика

1. **Никакого Thread-per-connection:** В Go можно держать миллионы открытых Websocket/TCP соединений. Память будет расходоваться в основном на стек горутин (минимум 2 КБ на G) и системные буферы чтения/записи сокетов. Потоки ОС при этом простаивают.
    
2. **Влияние системных вызовов (Syscalls):** Хотя Netpoller асинхронный, операции `Accept()` и первоначальный `Dial()` по-прежнему совершают синхронные блокирующие вызовы (внутри `sysmon` или обернутые в `entersyscall`). При экстремальном количестве новых соединений в секунду (Connection Flood) количество OS-подоков (M) в Go-приложении может кратковременно вырасти.
    
3. **Zero-Copy и `net.Buffers`:** При отправке данных по сети (особенно тяжелых файлов или пачек заголовков) используйте тип `net.Buffers` (метод `WriteTo`). Он под капотом использует системный вызов `writev` (Scatter-Gather I/O), минимизируя аллокации и копирование памяти между User Space и Kernel Space.
