Под капотом (channel) канал в Go — это **обычная структура данных в оперативной памяти (в куче/Heap)**. Управление каналами происходит целиком в пространстве пользователя (User Space) силами самого рантайма Go, без вовлечения ядра ОС.

Если заглянуть в исходники рантайма Go (файл `src/runtime/chan.go`), мы увидим, что канал — это структура, которая называется **`hchan`**.

## Анатомия структуры `hchan`

Вот из чего на самом деле состоит канал:

Go

``` go
type hchan struct {
    qcount   uint           // Сколько элементов сейчас лежит в буфере
    dataqsiz uint           // Размер буфера (емкость, которую мы передали в make(chan T, size))
    buf      unsafe.Pointer // Указатель на массив (кольцевой буфер), где физически лежат данные
    elemsize uint16         // Размер одного элемента в байтах
    closed   uint32         // Флаг: закрыт канал или нет (0 или 1)
    elemtype *_type         // Тип данных в канале (нужен для Garbage Collector)
    sendx    uint           // Индекс в буфере, куда будет записан следующий элемент (курсор записи)
    recvx    uint           // Индекс в буфере, откуда будет прочитан следующий элемент (курсор чтения)
    recvq    waitq          // Очередь заблокированных горутин, которые ЖДУТ данные из канала
    sendq    waitq          // Очередь заблокированных горутин, которые ЖДУТ, чтобы ЗАПИСАТЬ данные
    lock     mutex          // Мьютекс для защиты ВСЕХ полей этой структуры при конкурентном доступе
}
```

## 3 кита, на которых держится канал

По сути, рантайм делает за нас всю грязную работу, объединяя три простые вещи:

### 1. Кольцевой буфер (`buf`, `sendx`, `recvx`)

Если канал буферизированный (`make(chan int, 5)`), данные складываются в обычный массив в памяти. Чтобы не двигать элементы туда-сюда при чтении, массив закольцован. Индексы `sendx` (куда писать) и `recvx` (откуда читать) просто ходят по кругу.

### 2. Обычный Мьютекс (`lock`)

Да, каналы — это **не lock-free структуры**. Под капотом у каждого канала есть честный, очень быстрый внутренний мьютекс (`runtime.mutex`). Когда горутина пишет или читает из канала, она первым делом делает `lock()`, а в конце — `unlock()`. Каналы безопасны для конкурентного использования именно потому, что внутри они защищены мьютексом.

### 3. Две очереди ожидания (`recvq`, `sendq`)

Это самое интересное. Очереди имеют тип `waitq` и представляют собой двусвязные списки из структур **`sudog`**.

`sudog` — это, грубо говоря, обертка над заснувшей горутиной (`G`), в которой записано: какая именно горутина ждет и по какому адресу в памяти лежит (или куда нужно положить) её значение.

## Как это работает в динамике (Пример без буфера)

Представь сценарий: **Горутина G1​ пытается прочитать данные из пустого небуферизированного канала `ch <- v`.**

1. G1​ захватывает `lock` канала.
    
2. Видит, что канал пуст, а буфера нет. Значит, лететь дальше нельзя — нужно блокироваться.
    
3. Рантайм Go создает структуру `sudog`, упаковывает туда указатель на G1​ и адрес переменной, куда надо положить данные.
    
4. Этот `sudog` складывается в очередь ожидания чтения **`recvq`**.
    
5. Функция планировщика `gopark()` меняет статус G1​ на `_Gwaiting`, отвязывает её от текущего потока ОС (M) и отправляет спать.
    
6. Канал отпускает свой `lock`. Поток ОС не заблокирован — он берет другую горутину из очереди и работает.
    

### Магия прямой копии (Direct Copy)

Спустя время приходит **Горутина G2​ и хочет записать данные в этот же канал.**

1. G2​ захватывает `lock` канала.
    
2. Смотрит в очередь `recvq` и видит, что там грустит заснувшая G1​.
    
3. **Оптимизация рантайма:** Чтобы не тратить время, Go делает фокус. Он берет данные из памяти G2​ и **напрямую копирует их в память заснувшей G1​** (адрес которой сохранен в `sudog`). Скопировали из стека в стек, минуя всякие буферы!
    
4. Рантайм вызывает функцию `goready()`. Статус G1​ меняется на `_Grunnable`, и она отправляется в очередь планировщика. Скоро она проснется и поймет, что данные уже у нее в переменной.
    
5. Канал делает `unlock`.
    

## Резюме для Senior

Канал — это высокоуровневая абстракция над **кольцевым буфером, мьютексом и очередью заснувших горутин**. Никаких сокетов, никакой сети. Вся магия блокировки и просыпания горутин на каналах — это чистая работа планировщика Go (`GMP`), который перекладывает структуры в памяти в User Space.
