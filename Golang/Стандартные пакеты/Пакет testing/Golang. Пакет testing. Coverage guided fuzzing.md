# Golang. Пакет testing. Coverage guided fuzzing

## Назначение

Coverage guided fuzzing — механизм, который помогает fuzzing engine выбирать **интересные входные данные**.

Главная идея:

> Fuzzer не просто генерирует случайные значения, а сохраняет те, которые открывают новые пути выполнения программы.

---

## Общая схема

```
seed corpus
      |
      ↓
mutation (изменение input)
      |
      ↓
запуск fuzz function
      |
      ↓
сбор coverage
      |
      ↓
появился новый путь?
      |
  +---+---+
  |       |
 да      нет
  |       |
сохранить отбросить
```

---

# Как fuzzing понимает новое покрытие

Fuzzing использует **instrumentation**.

Перед запуском fuzzing код компилируется с дополнительной логикой.

Было:

```
if password == "ADMIN123" {
	panic("bug")
}
```

После инструментирования концептуально становится:

```
coverage[1]++

if password == "ADMIN123" {

	coverage[2]++

	panic("bug")
}
```

Эти счётчики позволяют понять:

- какие блоки кода выполнялись;
- какие ветки были пройдены.

---

## Пример

Код:

```
func Check(password string) {

	if len(password) < 5 {
		return
	}

	if password[0] != 'A' {
		return
	}

	if password == "ADMIN123" {
		panic("bug")
	}
}
```

---

Seed:

```
hello
```

Выполнение:

```
len(password) < 5     ❌
password[0] == 'A'    ❌
panic                 ❌
```

Coverage:

```
001
```

---

Fuzzer делает mutation:

```
hello
 ↓
Apple
```

Теперь:

```
len(password) < 5     ❌
password[0] == 'A'    ✅
panic                 ❌
```

Coverage:

```
011
```

Появился новый путь.

Go сохраняет:

```
hello
Apple
```

---

Дальше:

```
Apple
 ↓
ADMIN123
```

Получаем:

```
len(password) < 5     ❌
password[0] == 'A'    ✅
panic                 ✅
```

Coverage:

```
111
```

Найден новый путь.

---

# Почему он идёт к ADMIN123, а не к WRONGPASS123

Fuzzer **не знает**, что существует:

```
ADMIN123
```

Он не понимает смысл строк.

Он работает так:

```
Apple
 |
 +-- случайные изменения
 |
 +-- новый путь?
        |
        +-- да → сохранить
        |
        +-- нет → забыть
```

Например:

```
Apple
 ↓
WrongPASS123
```

может быть сгенерировано.

Но:

```
password[0] == 'A'
```

перестанет выполняться.

Coverage хуже:

```
001
```

вместо:

```
011
```

Поэтому такой input не становится основой для дальнейших мутаций.

---

# Что именно измеряет coverage

Не процент покрытия:

```
80% кода
```

как при:

```
go test -cover
```

А набор выполненных путей.

Например:

```
input 1:

101001


input 2:

101101
    ^
 новый участок
```

Второй input интереснее.

---

# Mutation + Coverage

Mutation сама по себе случайная:

```
hello
 ↓
Hello
 ↓
Apple
 ↓
ADMIN123
```

Но coverage выполняет роль фильтра:

```
новый путь?
      |
      ↓
оставить input
```

Получается принцип:

```
генерация
+
отбор по coverage
```

# Что важно понимать разработчику

Ты не управляешь этим механизмом.

Ты пишешь:

```
func FuzzParser(f *testing.F) {

	f.Add([]byte(`{"id":1}`))

	f.Fuzz(func(
		t *testing.T,
		data []byte,
	) {

		Parse(data)

	})

}
```

Дальше Go сам:

- компилирует код с instrumentation;
- генерирует данные;
- собирает coverage;
- выбирает интересные inputs;
- сохраняет corpus.

## Для собеседования

> Coverage guided fuzzing — это механизм выбора новых входных данных на основе покрытия кода. Во время fuzzing код запускается с instrumentation, которая позволяет отслеживать выполненные пути. Если новый input открывает новый путь выполнения, он сохраняется в corpus и используется для дальнейших мутаций. Fuzzer не понимает структуру данных или бизнес-логику, он только оптимизирует поиск по изменению покрытия.
