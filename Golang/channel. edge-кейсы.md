# Edge-кейсы каналов в Golang

Каналы — мощный инструмент, но их неправильное использование ведёт к дедлокам, паникам и утечкам горутин. Вот основные грабли.

## 1. Состояния канала и операции

| Операция               | nil channel        | Открытый канал                             | Закрытый канал                        |
| ---------------------- | ------------------ | ------------------------------------------ | ------------------------------------- |
| **Отправка** `ch <- v` | Блокирует навсегда | Блокирует, если нет получателя/буфер полон | **Паника** `send on closed channel`   |
| **Получение** `<-ch`   | Блокирует навсегда | Блокирует, если нет данных                 | Возвращает **zero value**, `ok=false` |
| **Close** `close(ch)`  | **Паника**         | Успешно                                    | **Паника** `close of closed channel`  |

## 2. Nil-каналы: главный враг дедлока

**Проблема:** Неинициализированный канал (`var ch chan int`) — это `nil`. Любая операция с ним блокирует горутину **навсегда**.

```go
var ch chan int  // nil
ch <- 1          // deadlock: main заблокирован навсегда 
```

**Почему это опасно:**
- Если блокируется **main** → `fatal error: all goroutines are asleep - deadlock!` 
- Если блокируется **дочерняя горутина** → она утекает, но программа продолжает работу (утечка горутин) 

**Трюк с `select`:** В `select` case с `nil`-каналом **никогда не выбирается** (блокируется). Это можно использовать для динамического включения/выключения веток, но легко получить дедлок, если все case'ы nil и нет `default` .

## 3. Закрытие канала: "Правило одного отправителя"

**Золотое правило:** Канал закрывает **только отправитель**, и только **один раз** .

```go
// НЕПРАВИЛЬНО: получатель закрывает канал
go func() {
    close(ch) // Паника, если отправитель ещё пишет
}()

// ПРАВИЛЬНО: отправитель владеет close
go func() {
    defer close(ch)
    for _, v := range items {
        ch <- v
    }
}()
```

**Почему так:**
- Отправка в закрытый канал → **panic** (необратимая) 
- Повторное закрытие → **panic** 
- `recover()` может перехватить эту панику, но это плохая практика — лучше не доводить 

**Если отправителей несколько** (fan-in): ни один из них не должен закрывать канал. Используй `sync.WaitGroup`, чтобы дождаться всех, и **отдельная горутина** закрывает канал после `wg.Wait()` .

## 4. Горутин-лики (утечки)

**Проблема:** Горутина, навсегда заблокированная на канале, никогда не будет собрана GC. Это утечка.

**Сценарии:**
- **Отправка без получателя:** Буферизованный канал заполнен, никто не читает — отправитель висит вечно .
- **Получение без отправки:** Читатель ждёт данные, которые никто не отправит и не закроет канал .
- **Бесконечный генератор:** Горутина пишет в канал, а потребитель давно ушёл .

**Решение — `context.Context`:**
```go
func producer(ctx context.Context) <-chan int {
    ch := make(chan int)
    go func() {
        defer close(ch)
        for {
            select {
            case ch <- val:
            case <-ctx.Done():
                return // Выход по отмене
            }
        }
    }()
    return ch
}
```
Также используй `for range ch` — цикл автоматически завершится при закрытии канала .

## 5. `select` и недетерминизм

**Проблема:** При нескольких готовых case'ах `select` выбирает **случайный**. Порядок не гарантирован.

```go
select {
case v := <-ch1:
case v := <-ch2: // Какой сработает — непредсказуемо
}
```

**Следствие:** Не полагайся на порядок обработки. Если нужна строгая последовательность — используй один канал или mutex.

## 6. Буферизованные каналы: backpressure и память

**Проблема:** Большой буфер маскирует потерю backpressure. Продюсер может забить память данными, которые потребитель никогда не прочитает .

```go
ch := make(chan int, 1000000) // Плохо: продюсер не тормозит
```

**Рекомендация:**
- Небуферизованные каналы дают **естественный backpressure**: отправитель ждёт получателя .
- Буфер используй только для сглаживания коротких пиков, а не для "чтобы не блокировалось".
- Всегда комбинируй с `context` для отмены .

## 7. Гонки данных вне каналов

**Критический нюанс:** Каналы синхронизируют **только значения, которые через них передаются**. Они **не защищают** другие общие переменные.

```go
var counter int
ch := make(chan int)

go func() {
    for i := 0; i < 1000; i++ {
        ch <- i
        counter++ // RACE! Канал это не защищает
    }
}()
```
Для защиты `counter` нужен `sync/atomic` или `sync.Mutex` .

## 8. Краткая памятка

| Ситуация | Последствие | Решение |
|---|---|---|
| Отправка в nil | Вечный блок | Инициализируй `make(chan T)` |
| Отправка в closed | **Panic** | Только отправитель закрывает, один раз |
| Close closed | **Panic** | Защити `sync.Once` или флагом |
| Нет получателя | Утечка горутины | `context.Done()` + `select` |
| Много отправителей | Нельзя закрывать | `sync.WaitGroup` + отдельный closer |
| Большой буфер | Утечка памяти, нет backpressure | Малый буфер или unbuffered |

**Главное правило:** Канал — это протокол передачи владения. Закрывает его тот, кто отправляет. Читает — тот, кому данные нужны. И всегда думай о `context` для отмены.
