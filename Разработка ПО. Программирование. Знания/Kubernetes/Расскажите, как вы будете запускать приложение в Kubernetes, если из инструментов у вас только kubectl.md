Запуск приложения в Kubernetes, имея в руках _только_ утилиту `kubectl`, — это отличная проверка на понимание базы. В такой ситуации мы не можем рассчитывать на Helm-чарты, CI/CD пайплайны или GitOps-операторы вроде ArgoCD.

Все придется делать вручную, и у нас есть два пути: **императивный** (быстрый, одной командой в терминале) и **декларативный** (правильный, через создание манифестов «на лету»).

Ниже подробно описано, как пошагово развернуть приложение, сделать его доступным и проверить работу.

## Способ 1: Полностью императивный (Быстрый старт)

Этот способ хорош, если нужно «побыстрому» что-то протестировать. Мы не пишем YAML-файлы, а даем прямые команды кластеру.

### Шаг 1. Запуск самого приложения (Deployment)

Создаем объект `Deployment`, который скачает образ из реестра (например, Docker Hub) и запустит контейнер:

``` bash
kubectl create deployment my-app --image=nginx:alpine --replicas=3
```

_Здесь мы запускаем приложение `my-app` на базе образа `nginx:alpine` сразу в 3 экземплярах (подах) для отказоустойчивости._
### Шаг 2. Открытие доступа (Service)

Поды внутри кластера изолированы и могут умирать/рождаться с новыми IP-адресами. Чтобы к приложению можно было надежно обращаться, создаем `Service`:

``` bash
kubectl expose deployment my-app --type=ClusterIP --port=80 --target-port=80
```

_Если вы работаете в облаке (AWS, GCP, Yandex Cloud) и вам нужен внешний IP-адрес для доступа из интернета, замените `--type=ClusterIP` на `--type=LoadBalancer`._

## Способ 2: Декларативный (Правильный подход)

В реальной работе императивный подход не любят: конфигурацию нельзя сохранить в Git или детально настроить. Но так как у нас есть _только_ `kubectl`, мы можем заставить его **сгенерировать YAML-шаблоны за нас**.

### Шаг 1. Генерируем и применяем Deployment

Используем флаги `--dry-run=client -o yaml`, чтобы `kubectl` не создавал объект в кластере, а просто вывел его структуру, и сохраняем её в файл:

Bash

``` bash
kubectl create deployment my-app --image=nginx:alpine --replicas=3 --dry-run=client -o yaml > deployment.yaml
```

Теперь у нас есть файл `deployment.yaml`. Если нужно, мы можем отредактировать его прямо в терминале с помощью `nano` или `vim` (например, добавить переменные окружения или лимиты по ресурсам).

Применяем файл в кластер:

``` bash
kubectl apply -f deployment.yaml
```

### Шаг 2. Генерируем и применяем Service

Точно так же генерируем манифест для сетевого доступа:

``` bash
kubectl expose deployment my-app --type=ClusterIP --port=80 --target-port=80 --dry-run=client -o yaml > service.yaml
```

Применяем его:

``` bash
kubectl apply -f service.yaml
```

## Шаг 3: Проверка статуса (Диагностика)

После отправки манифестов нужно убедиться, что всё завелось. Используем только `kubectl`:

1. **Проверяем статус подов:**
    ``` bash
    kubectl get pods -l app=my-app
    ```
    _Ищем статус `Running`. Если там `CrashLoopBackOff` или `ErrImagePull`, что-то пошло не так._
2. **Смотрим логи (если приложение не запускается):**
    ``` bash
    kubectl logs -l app=my-app --tail=50
    ```
3. **Описываем состояние пода для поиска скрытых ошибок:**
    ``` bash
    kubectl describe pod <имя_любого_пода_из_списка>
    ```

_В самом низу вывода будет блок `Events` — там видно, скачался ли образ и хватило ли поду памяти._

## Шаг 4: Как достучаться до приложения (Проверка работы)

Если вы создали сервис с типом `ClusterIP`, приложение доступно только внутри сети Kubernetes. Как проверить его снаружи, имея только `kubectl`?

### Вариант А: Проброс портов (Port-Forwarding)

Это самый простой способ «пощупать» приложение со своей локальной машины. Мы временно пробрасываем порт из кластера на свой компьютер:

``` bash
kubectl port-forward svc/my-app 8080:80
```

Теперь вы можете открыть браузер на своем компьютере, перейти по адресу `http://localhost:8080` и увидеть приветственную страницу вашего приложения.

### Вариант Б: Тест "изнутри" кластера

Можно запустить временный под с утилитой `curl` прямо внутри сети кластера и "постучаться" в созданный ранее сервис:

``` bash
kubectl run test-curl --image=curlimages/curl -i --tty --rm -- curl http://my-app
```

_Эта команда создаст под, выполнит запрос к `http://my-app`, выведет ответ в терминал и сразу же удалит этот временный под (`--rm`)._

---
В общем виде последовательность действий выглядит следующим образом:  
  
1. Для запуска в Kubernetes приложение должно быть упаковано в контейнер, поэтому первым шагом будет поместить приложение в контейнер.
2. Затем нужно запустить контейнер в виде набора реплик (подов). Для этого используем Deployment.
3. Для того чтобы приложение было доступно в интернете и к нему можно было подключиться, нужно настроить сервис LoadBalancer, который позволит присвоить публичный IP-адрес и подключиться к кластеру из внешней сети.
4. Чтобы маршрутизировать пришедший через балансировщик трафик до приложения, в кластере должен быть создан Ingress, описывающий правила маршрутизации, и запущен Ingress-контроллер.

Проделать все это можно через kubectl, командную строку по сути. Это императивный и самый простой способ, когда мы как бы говорим Kubernetes «сделай это и это».  
  
Второй способ, который применяется уже в промышленной эксплуатации, — это управление через декларативные манифесты, в которых мы описываем желаемое состояние, а Kubernetes уже сам решает, какие действия для этого нужно сделать. Затем эти манифесты отправляем в Kubernetes c помощью команды kubectl apply.
