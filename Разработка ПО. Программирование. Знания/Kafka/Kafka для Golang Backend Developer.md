Эта шпаргалка разработана специально для Go-разработчиков. В ней нет «воды» про общую теорию, только хардкорная специфика: архитектура, выбор драйверов, паттерны конкурентности в Go, обработка ошибок и особенности работы с памятью в рантайме.

## 1. Выбор Клиента (Драйвера) в Go

В экосистеме Go есть три главных игрока. Выбор определяет перформанс и стабильность вашего сервиса.

### **`github.com/confluentinc/confluent-kafka-go/v2`**

- **Что это:** Обёртка над нативной Си-библиотекой `librdkafka`.
- **Плюсы:** Официальный клиент от создателей Kafka. Самый быстрый, фичастый и стабильный. Поддерживает Exactly-Once (EOS), транзакции и новейшие протоколы авторизации.
- **Минусы:** **CGO**. Из-за Си-подложки усложняется Docker-сборка (нужен `gcc` и `musl`/`glibc`). Сильно бьет по кросс-компиляции. При панике внутри Си-кода рантайм Go не сможет показать красивый стек-трейс.

### **`github.com/twmb/franz-go`**

- **Что это:** Современный, написанный на 100% чистом Go клиент.
- **Плюсы:** **Полноценный pure Go.** Феноменальная производительность (часто обгоняет `librdkafka` за счет оптимизации аллокаций памяти в Go). Отличный API, поддерживающий современные фичи Kafka (до v3.x+). Идеально дружит с планировщиком Go (`GMP`).
- **Минусы:** Меньше Enterprise-обвязки (например, интеграции с Confluent Schema Registry нужно докручивать сторонними пакетами).

### **`github.com/IBM/sarama`**

- **Что это:** Старый pure Go клиент (бывший Shopify).
- **Плюсы:** Самый популярный исторически, много старого кода написано на нем.
- **Минусы:** Перегруженный и неинтуитивный API с каналами внутри конфигурации. Исторически страдал от утечек памяти при неправильной настройке ребалансировки. Постепенно уступает место `franz-go`.

> **Рекомендация для Senior:** Для критически важных High-Load систем с транзакциями — **`confluent-kafka-go`**. Для чистых микросервисов, быстрой сборки и Docker-контейнеров без боли с CGO — **`franz-go`**.

## 2. Паттерны Продюсера (Producer)

Главный нюанс Продюсера в Go — баланс между пропускной способностью (Throughput) и гарантией доставки (Durability).

### Важные конфигурационные параметры:

- **`acks`**:
    - `0` — Отправили и забыли. Максимальная скорость, возможна потеря данных.
    - `1` — Ждем подтверждения только от Leader-брокера. Баланс.
    - `all` (или `-1`) — Ждем подтверждения от лидера и всех ISR (синхронных реплик). Гарантия надежности.
- **`CompressionType`**: Всегда включайте сжатие (`lz4` или `zstd`). Это экономит CPU на аллокациях строк и снижает нагрузку на сеть.

### Паттерн: Асинхронная отправка с пулом горутин (franz-go)

Не нужно блокировать HTTP-воркер на отправке сообщения. Используйте асинхронный API.

Go

``` go
// Пример концепта отправки
func ProduceMessage(cl *franz.Client, ctx context.Context, topic string, payload []byte) {
    record := &franz.Record{Topic: topic, Value: payload}
    
    // Асинхронный вызов. Под капотом пакет сам собирает батчи (Batching)
    cl.Produce(ctx, record, func(r *franz.Record, err error) {
        if err != nil {
            // Обработка ошибки отправки (например, лог или метрика)
            log.Printf("Failed to produce: %v", err)
        }
    })
}
```

## 3. Паттерны Консумента (Consumer) и Специфика Go

В Kafka параллелизм масштабируется **партициями (Partitions)**. Один поток (горутина) читает одну партицию внутри Consumer Group.

### Критическая ошибка: «Горутина на каждое сообщение»

**Антипаттерн:** Вычитывать батч из Kafka, запускать `go process(msg)` на каждое сообщение и тут же делать Commit.

- **Почему это сломает логику:** Горутины планируются хаотично. `G2` может обработать сообщение быстрее, чем `G1`. Если вы закоммитите оффсет `G2`, а `G1` упадет, то при перезапуске сообщение из `G1` **никогда больше не прочитается** (Data Loss).
    

### Правильный паттерн: Fan-Out по Worker Pool с Worker-specific каналами

Если обработка сообщения долгая (запрос в БД, сторонний API), а партиций мало, нужно распараллелить обработку, сохраняя порядок оффсетов.

1. Читаем сообщения последовательно из Kafka в цикле.
    
2. Распределяем сообщения по воркерам на основе ключа (`msg.Key`) с помощью хэширования: `workerID = hash(key) % totalWorkers`.
    
3. Каждый воркер имеет свой Go-канал (`chan *franz.Record`).
    
4. Коммитим оффсеты строго последовательно из основного потока чтения.
    

### Смерть Консумента: Ребалансировка (Heartbeat vs Processing)

- **`session.timeout.ms`**: Время, за которое брокер считает консумент мертвым, если тот не прислал пинг (Heartbeat). Поток пингов в современных клиентах идет в отдельном фоновом потоке ОС (`M`).
    
- **`max.poll.interval.ms`**: Максимальное время между вызовами `Poll()` (чтением нового батча).
    
- **Ловушка:** Если ваш Go-код завис на обработке тяжелого батча (например, затупила база данных) дольше, чем `max.poll.interval.ms`, Kafka решит, что ваш консумент завис. Брокер выкинет его из группы и запустит **Ребалансировку (Rebalance)**. Сервис перестанет читать данные и начнет бесконечно пересобирать группу.
    

## 4. Обработка ошибок: Паттерн Dead Letter Queue (DLQ)

В отличие от RabbitMQ, в Kafka нельзя «отклонить одно сообщение и вернуть его в начало очереди» (`nack`), потому что Kafka — это append-only лог. Оффсет должен идти только вперед.

### Стратегия обработки ядовитых сообщений (Poison Pills):

1. **Retry Topic:** Если ошибка временная (мигнула сеть базы данных), отправляем сообщение в специальный топик `topic_name_retry` и коммитим оффсет в основном топике. Отдельный консумент читает `retry` топик с задержкой.
    
2. **DLQ (Dead Letter Queue):** Если сообщение сломано (битый JSON, не проходит валидацию), горутина-консумент отправляет его в топик `topic_name_dlq`. После этого основной оффсет сдвигается вперед. Бизнес-логика не блокируется.
    

## 5. Шпаргалка по конфигурации для продакшена

Сохраните эти настройки как базовый стандарт для микросервисов на Go:

|Параметр|Значение для Надежности (Гарантия)|Значение для High-Load (Скорость)|Читать как|
|---|---|---|---|
|`acks`|`all`|`1`|Сколько реплик должны подтвердить запись.|
|`enable.auto.commit`|`false`|`true` (с осторожностью)|Ручной коммит оффсетов в Go-коде после реальной обработки.|
|`compression.type`|`zstd` или `lz4`|`lz4`|Алгоритм сжатия батчей.|
|`max.in.flight.requests.per.connection`|`1` (или `5` с idempotence)|`5`|Сколько нелимитированных запросов может быть в пути (влияет на порядок сообщений).|

## 6. Взаимодействие с Рантаймом Go (Память и Оптимизация)

1. **Пул объектов для Батчей:** При вычитке миллионов сообщений в секунду из Kafka, горутины будут генерировать гигантское количество мусора (миллионы структур `Message` или `[]byte`). Используйте **`sync.Pool`** для переиспользования буферов байт, чтобы снизить нагрузку на Garbage Collector (`GC`).
    
2. **Прокидывание `context.Context`:** Всегда передавайте `ctx` во все методы `Produce` и `Poll`. Это позволит корректно завершать работу горутин (Graceful Shutdown) при деплое в Kubernetes (по сигналу `SIGTERM`).
    
3. **Graceful Shutdown паттерн:**
    

Go

```
// Перед выходом из приложения обязательно закрываем клиент
defer client.Close() 

// Для продюсеров обязательно вызывайте Flush перед выходом
defer client.Flush(ctx)
```

Без вызова `Flush()` сообщения, которые на момент остановки сервиса скопились в памяти Go-клиента в батчах, будут безвозвратно утеряны.
