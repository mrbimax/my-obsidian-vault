Вопрос бьет прямо в самую глубокую и исторически сложную болячку ядра Linux. Разработчики операционных систем десятилетиями пытались сделать для дисков аналог `epoll`, но уперлись в фундаментальные различия между сетью и персистентным хранилищем.

Если говорить на уровне Senior-инженера, причина, почему Netpoller не работает с файлами, кроется в **архитектуре виртуальной файловой системы (VFS) Linux** и механизме работы **Page Cache**.

Вот 3 главные причины, почему обычные файлы нельзя просто так подружить с `epoll` и неблокирующим IO.

## 1. Файловые дескрипторы диска всегда «готовы» (Спецификация POSIX)

Сетевой сокет — это классический стрим. Если в буфер сокета ничего не прилетело из сетевой карты, ядро знает: данных нет, можно вернуть `EAGAIN` и отправить поток спать.

С файлом на диске ситуация принципиально иная. С точки зрения VFS Linux, обычный файл **всегда готов к чтению**. У него нет понятия «данные еще не пришли по проводу», данные уже лежат на физических блинах HDD или ячейках SSD.

Если ты передашь дескриптор обычного файла в `epoll_ctl` с флагом `EPOLLIN`, `epoll` **мгновенно вернет управление** и скажет: _«Файл готов, читай!»_. Но когда горутина вызовет `read()`, поток ОС заблокируется. Почему? Потому что в дело вступает кэш ядра.

## 2. Проклятие Page Cache и синхронность драйверов

Когда приложение вызывает `read()` для файла, ядро Linux никогда не идет на диск напрямую. Оно сначала проверяет **Page Cache** (оперативную память, где ОС кэширует страницы диска).

1. **Page Cache Hit (Кэш-попадание):** Если страница файла уже в оперативной памяти, ядро мгновенно копирует данные в буфер Go. Это происходит в User Space / Kernel Space без вовлечения диска, операция занимает наносекунды. Это фактически неблокирующий вызов.
2. **Page Cache Miss (Кэш-промах):** Если данных в памяти нет, ядру нужно выполнить физический ввод-вывод (I/O).

Вот тут и скрыта главная проблема: драйвер файловой системы внутри ядра спроектирован так, что в момент кэш-промаха он переводит текущий поток ОС в состояние **Uninterruptible Sleep (`D state`)**. Поток физически засыпает и ждет прерывания от контроллера диска (SATA/NVMe).

У ядра Linux просто **нет механизма**, который позволял бы драйверу файловой системы (например, ext4 или xfs) сказать: _«Ой, страницы нет в кэше, верни-ка приложению `EAGAIN`, а я пока фоново подтяну её с NVMe»_. Системный вызов `read()` обязан дождаться окончания дисковой операции.

## 3. А как же Linux AIO и io_uring?

Ты можешь возразить: _«Но ведь в Linux есть механизмы асинхронного дискового ввода-вывода!»_. Да, они есть, но со своими огромными «но»:

### Попытка №1: Linux AIO (`io_submit`, `io_getevents`)

Появился давно, но для общего использования непригоден.

- **Главный минус:** Он работает **только** если файл открыт с флагом `O_DIRECT` (в обход Page Cache).
- Если ты отключаешь Page Cache, ты теряешь все оптимизации ОС, упреждающее чтение (read-ahead) и выравнивание. Тебе приходится писать свой менеджер кэша внутри приложения (как это делают базы данных вроде ScyllaDB или ClickHouse). Для рантайма Go общего назначения это неприемлемо. К тому же, на многих операциях (например, выделение места под файл) AIO все равно уходил в блокирующий синхрон.
### Попытка №2: Современный `io_uring` (Появился в Linux 5.1+)

Вот это уже настоящая революция. `io_uring` решает проблему асинхронного дискового (и сетевого) ввода-вывода через два разделяемых кольцевых буфера (Submission Queue и Completion Queue) в Shared Memory между User Space и Kernel Space. Ему не важен `O_DIRECT`, он умеет работать асинхронно с Page Cache.

**Почему Go до сих пор не перевел Netpoller на `io_uring` для файлов?**

1. **Обратная совместимость и портативность:** Go славится тем, что компилируется и работает везде одинаково (старые ядра Linux, macOS, Windows, BSD). `io_uring` требует свежих версий ядер, и его API долгое время стабилизировался.
2. **Безопасность:** В истории `io_uring` было критически много CVE (уязвимостей, связанных с правами доступа и памятью в ядре). Многие энтерпрайз-дистрибутивы (например, Red Hat) долгое время отключали его по умолчанию в целях безопасности.
3. **Сложность интеграции с GMP:** Архитектура `io_uring` подразумевает создание пула ядерных потоков (`io_wqe`), что начинает конфликтовать с собственным планировщиком Go.
## Как Go выкручивается сейчас?

Поскольку Netpoller бессилен перед дисковым I/O, рантайм Go использует проверенный временем костыль: **Thread Pool**.

Когда ты вызываешь `os.ReadFile()`, рантайм выполняет обычный синхронный syscall. Если происходит кэш-промах, поток ОС (`M`) честно засыпает в `D state`.

В этот момент поток мониторинга Go (`sysmon`) видит, что поток `M` заблокирован на системном вызове дольше ~20 микросекунд. `sysmon` насильно забирает у этого потока процессор `P` (логическое ядро планировщика) и отдаёт его другому, свободному потоку ОС (или создает новый поток через `startm`), чтобы остальные горутины не ждали, пока этот конкретный поток «рожает» данные с диска.

По сути, Go имитирует асинхронность диска, просто масштабируя количество тяжелых потоков операционной системы под капотом.
