**Nginx** — это высокопроизводительный [[HTTP]]-сервер, обратный [[прокси-сервер ]]([[Reverse Proxy]]) и [[балансировщик нагрузки]]. Он спроектирован на базе асинхронной, событийно-ориентированной архитектуры ([[Event-driven]]), что позволяет ему эффективно обрабатывать десятки тысяч одновременных соединений ([[C10K-проблема]]) при минимальном потреблении оперативной памяти.

## 🏗️ Архитектура Nginx

Nginx использует модульную архитектуру с одним управляющим процессом (**Master**) и несколькими рабочими процессами (**Worker**).

- **Master-процесс:** Читает и проверяет конфигурацию, управляет жизненным циклом Worker-процессов, применяет обновления «на лету» без остановки сервера. Не обрабатывает сетевые запросы клиентов.
    
- **Worker-процессы:** Выполняют всю реальную работу (сетевые соединения, чтение/запись на диск, проксирование). Обычно их количество настраивают равным числу ядер процессора (`worker_processes auto;`).
    

## 🗂️ Структура конфигурационного файла (`nginx.conf`)

Конфигурация строится по древовидному принципу и разделена на контексты (блоки):

Nginx

```
# Глобальный контекст (Main) — настройки процессов, логирования, системных лимитов
worker_processes auto;
pid /var/run/nginx.pid;

events {
    # Контекст событий — сетевые настройки (кол-во соединений на один Worker)
    worker_connections 1024;
}

http {
    # Контекст HTTP — глобальные настройки веб-сервера (MIME-типы, тайм-ауты, логи)
    include /etc/nginx/mime.types;
    gzip on;

    upstream backend_pool {
        # Блок балансировки серверов
        server 127.0.0.1:8081;
        server 127.0.0.1:8082;
    }

    server {
        # Контекст виртуального хоста (домен или IP + порт)
        listen 80;
        server_name example.com www.example.com;

        location / {
            # Контекст URI — правила обработки конкретных путей запроса
            root /var/www/html;
            index index.html;
        }

        location /api/ {
            # Проксирование на балансировщик
            proxy_pass http://backend_pool;
        }
    }
}
```

## 💻 Базовые команды CLI

|**Команда**|**Описание**|
|---|---|
|`nginx -t`|Проверить синтаксис конфигурационных файлов на ошибки|
|`nginx -s reload`|Перезапустить Nginx без прерывания текущих соединений (Hot Reload)|
|`nginx -s stop`|Немедленная жесткая остановка сервера|
|`nginx -s quit`|Плавная остановка (дать Worker-процессам завершить обработку запросов)|
|`nginx -v` / `nginx -V`|Показать версию Nginx / Версию и все скомпилированные модули|

## 🔄 Реверс-Прокси и проброс заголовков

Классическая настройка Nginx в качестве «щита» перед бэкендом (например, приложением на Go / Node.js). Важно корректно передавать реальные IP-адреса клиентов, иначе бэкенд будет видеть только IP-адрес самого Nginx.

Nginx

```
location /api/ v1/ {
    proxy_pass http://127.0.0.1:8080; # Куда перенаправлять трафик
    
    # Передача оригинальных заголовков клиента бэкенду
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # Настройки тайм-аутов для долгих запросов
    proxy_connect_timeout 90s;
    proxy_send_timeout 90s;
    proxy_read_timeout 90s;
}
```

## ⚖️ Балансировка нагрузки (`upstream`)

Nginx умеет распределять запросы между несколькими серверами бэкенда.

Nginx

```
upstream backend_servers {
    # 1. Round Robin (по умолчанию) — запросы идут строго по очереди
    # 2. Least Connections — запрос идет туда, где сейчас меньше всего активных соединений
    least_conn; 

    server app1.example.com:8080 weight=3; # weight=3 означает, что сюда пойдет в 3 раза больше запросов
    server app2.example.com:8080;
    server app3.example.com:8080 backup;  # backup включится только если app1 и app2 «упадут»
    server app4.example.com:8080 max_fails=3 fail_timeout=30s; # Проверка доступности
}
```

- **`ip_hash`:** Метод балансировки, привязывающий клиента к конкретному серверу по его IP-адресу (полезно для сохранения сессий / Stateful-приложений).
    

## ⚡ Оптимизация под высокую нагрузку (Highload Тюнинг)

Для выжимания максимума производительности из сетевого стека Linux и Nginx:

Nginx

```
# В секции Main:
worker_rlimit_nofile 65535; # Увеличиваем лимит дескрипторов файлов для процессов Nginx

events {
    worker_connections 4096; # Количество соединений на один воркер (Max clients = connections * workers)
    use epoll;               # Использовать самый эффективный метод обработки соединений в Linux
    multi_accept on;         # Воркер принимает все новые соединения сразу, а не по одному
}

http {
    # Эффективная работа с диском и сетью
    sendfile on;             # Копирование данных между дескрипторами напрямую в ядре (TCP Zero-Copy)
    tcp_nopush on;           # Отправка заголовков пакета одним куском (только вместе с sendfile)
    tcp_nodelay on;          # Отключение алгоритма Нагла (минимизирует задержки, пакеты уходят сразу)

    # Тайм-ауты для предотвращения удержания соединений медленными клиентами
    keepalive_timeout 65;    # Сколько держать keepalive-соединение открытым
    keepalive_requests 100;  # Макс. запросов через одно keepalive-соединение
    client_body_timeout 10;
    client_header_timeout 10;
    send_timeout 10;

    # Буферы (защита от записи временных файлов на диск)
    client_body_buffer_size 16k;
    client_header_buffer_size 1k;
    client_max_body_size 20m; # Максимальный размер загружаемого файла (например, аватарки)
}
```

## 📊 Полезные встроенные переменные

Внутри конфигурации (особенно в логах `log_format` и `proxy_set_header`) часто используются системные переменные:

|**Переменная**|**Что содержит**|
|---|---|
|`$remote_addr`|IP-адрес клиента (непосредственного отправителя пакета)|
|`$proxy_add_x_forwarded_for`|Цепочка IP-адресов, через которые прошел запрос (клиент + прокси)|
|`$host`|Имя хоста из заголовка запроса `Host`, либо имя сервера|
|`$request_uri`|Полный первоначальный URI запроса с аргументами (например, `/index.php?id=1`)|
|`$uri`|Текущий URI в процессе обработки (может меняться после `rewrite`)|
|`$status`|HTTP-статус ответа (например, `200`, `404`, `502`)|
|`$request_time`|Полное время обработки запроса Nginx в секундах с миллисекундами|
|`$upstream_response_time`|Время, которое затратил бэкенд на ответ (без учета сети до Nginx)|

## 🔒 Безопасность: Ограничение частоты запросов (Rate Limiting)

Защита от DDoS-атак и брутфорса эндпоинтов авторизации (основана на алгоритме **Leaky Bucket**).

Nginx

```
http {
    # Создаем зону памяти "login_limit" размером 10MB (хватит на ~160к IP) со скоростью 5 запросов в секунду
    limit_req_zone $binary_remote_addr zone=login_limit:10m rate=5r/s;

    server {
        location /api/v1/auth/login {
            # Применяем лимит. burst=10 позволяет кратковременно пропустить до 10 запросов сверх лимита,
            # но они будут выстроены в очередь. nodelay предотвращает задержки внутри burst-лимита.
            limit_req zone=login_limit burst=10 nodelay;
            
            proxy_pass http://backend;
        }
    }
}
```
