# Kubernetes для Go-разработчика

## 1. Базовая архитектура (Control Plane vs Worker Nodes)
Kubernetes работает по схеме Master-Worker.

### Control Plane (Master Node) — мозг кластера:
* **kube-apiserver** — точка входа для всех запросов (CLI, UI, внутренние компоненты). Единственный компонент, общающийся с хранилищем.
* **etcd** — распределенное, согласованное (CP по теореме CAP) хранилище типа ключ-значение. Хранит все состояние кластера.
* **kube-scheduler** — отслеживает созданные Pod'ы и выбирает, на какой ноде их запустить (учитывая ресурсы, affinity/anti-affinity).
* **kube-controller-manager** — запускает фоновые контроллеры (Node Controller, ReplicaSet Controller и др.), которые следят за соответствием текущего состояния кластера желаемому.

### Worker Nodes — где выполняются наши приложения:
* **kubelet** — агент на каждой ноде. Следит за тем, чтобы контейнеры были запущены и работали в соответствии с PodSpecs.
* **kube-proxy** — сетевой прокси, отвечает за сетевые правила (iptables/IPVS) на нодах, обеспечивает работу сервисов (Service).
* **Container Runtime** — среда выполнения контейнеров (обычно **containerd** или **CRI-O**).

## 2. Основные абстракции (Ресурсы k8s)

* **Pod (Под)** — минимальная неделимая единица k8s. Группа из одного или нескольких контейнеров (например, контейнер с вашим Go-приложением + sidecar-контейнер для логов). Они делят один IP-адрес и network namespace.
* **Deployment** — декларативное описание желаемого состояния для Pod'ов. Управляет обновлением версий (RollingUpdate), масштабированием и созданием `ReplicaSet`.
* **ReplicaSet** — гарантирует, что в кластере одновременно запущено заданное количество идентичных Pod'ов.
* **Service (Сервис)** — абстракция, которая определяет логический набор Pod'ов и политику доступа к ним. Обеспечивает стабильный IP-адрес и балансировку трафика между Pod'ами (типы: `ClusterIP`, `NodePort`, `LoadBalancer`).
* **Ingress** — управляет внешним доступом к сервисам в кластере (обычно HTTP/HTTPS). Работает как Reverse Proxy (на базе Nginx, Traefik, Envoy).

## 3. Жизненный цикл Pod'а и Пробы (Probes)
Для Go-разработчика критически важно правильно настроить эти три пробы в `PodSpec` через HTTP-хэндлеры или gRPC:

1.  **Liveness Probe**
    * *Зачем:* Проверяет, живо ли приложение внутри контейнера.
    * *Действие k8s:* Если проба падает, k8s **перезапускает** контейнер.
    * *В Go:* Не должна проверять внешние зависимости (БД, кэш). Должна возвращать `200 OK`, если рантайм Go не завис (например, нет дедлока).
2.  **Readiness Probe**
    * *Зачем:* Проверяет, готово ли приложение принимать входящий трафик.
    * *Действие k8s:* Если проба падает, k8s **исключает Pod из балансировки** (трафик на него не идет), но не перезапускает.
    * *В Go:* Здесь нужно проверять подключение к БД, Kafka, Redis. Если база «легла», под должен временно отключиться от трафика.
3.  **Startup Probe**
    * *Зачем:* Проверяет, запустилось ли приложение (актуально для «тяжелых» приложений).
    * *Действие k8s:* Пока эта проба не пройдет, Liveness и Readiness пробы отключены.

## 4. Специфика Go в Kubernetes (Что спрашивают на собеседованиях)

### 1. Проблема `GOMAXPROCS` и CPU Limits
* **Суть:** По умолчанию Go runtime видит количество процессоров хоста (ноды), а не лимиты, установленные для контейнера (`resources.limits.cpu`).
* **Проблема:** Если лимит контейнера — `1 CPU`, а на ноде `64 CPU`, Go создаст слишком много системных потоков (threads). Это приведет к жесткому **CPU Throttling** (замедлению работы) со стороны k8s CFS scheduler.
* **Решение:** Использовать библиотеку от Uber — `go.uber.org/automaxprocs` в `main.go`. Она автоматически считывает cgroups лимиты и выставляет правильный `GOMAXPROCS`.

### 2. Graceful Shutdown (Плавное завершение)
При удалении Pod'а (деплой, масштабирование):
1.  Pod переводится в состояние `Terminating`.
2.  k8s посылает процессу сигнал **SIGTERM**.
3.  Начинается тиканье таймера `terminationGracePeriodSeconds` (по умолчанию 30с).
4.  Если процесс не завершился сам, k8s шлет **SIGKILL**.

* **В Go коде:** Нужно обязательно отлавливать `os.Interrupt` и `syscall.SIGTERM`, закрывать сетевые соединения (`http.Server.Shutdown()`), останавливать воркеры и коннекты к БД, давая им завершить текущие задачи.

### 3. Оптимизация Docker-образов
* Для Go приложений нужно использовать **multi-stage builds**.
* Финальный образ должен быть минимальным: на базе `alpine`, `distroless` или вообще `scratch` (пустой образ, содержащий только ваш бинарник).
* *Плюсы:* Меньше уязвимостей, быстрее скачивается в кластере (быстрее деплой и автомасштабирование).

## 5. Полезные шпаргалки (Шпаргалка по kubectl)

```bash
# Посмотреть логи конкретного пода
kubectl logs <pod-name> -n <namespace> --tail=100 -f

# Порт-форвардинг с локальной машины на под в кластере (удобно для дебага БД/сервиса)
kubectl port-forward pod/<pod-name> 8080:8080

# Посмотреть подробную информацию о ресурсе (причины падения, события)
kubectl describe pod <pod-name>

# Быстро посмотреть загрузку ресурсов нод или подов (нужен Metrics Server)
kubectl top pods
kubectl top nodes
